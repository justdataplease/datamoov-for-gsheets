# Adding a DataMoov Sheets connector

DataMoov Sheets is a standalone Apps Script app. It borrows DataMoov's registry architecture and the campaign optimizer's report definitions; it does not call either backend. It uses a workflow inspired by [Supermetrics query creation](https://docs.supermetrics.com/docs/how-to-create-a-supermetrics-query-in-google-sheets): choose a source and account, select a report/date range/fields, choose an output location, and refresh a saved report.

One file under `src/connectors/` calls `dmvRegisterConnector_` with its metadata, credential fields, exact allowed hosts, and report definitions. The sidebar, storage, transport, scheduler, preview, and Sheets writer must stay independent of provider identities. A new compatible connector must work without adding a switch or provider allow-list to those shared layers.

Each report declares `id`, `label`, `description`, `fields`, `configFields`, `dateRange`, and `fetch(ctx)`. Optional `discoverFields(ctx)` returns account-specific column descriptors; the catalog derives the "Load columns" button from its presence, so do not declare a separate flag. Use the helpers in `dmv_connector_helpers.js`: `dmvSelectFields_(ctx.fields, available)` resolves the selection, `dmvNeedsDiscovery_` tells whether a discovery call is required, `dmvNumber_`/`dmvTextValue_` coerce provider values, `dmvAppendPage_` enforces the row budget, `dmvUtcWindow_` gives the inclusive date range in UTC milliseconds, and `dmvGoogleAuthFields_`/`dmvBearer_` cover Google authorization. Fields use `{key,label,type,role,default}`. Mark a small default set explicitly. A credential descriptor uses `secret:true` or `type:'password'`; secrets are never returned by bootstrap or connection summaries. Conditional forms use `showWhen:{key,value}`.

`fetch` returns `{columns,rows,metadata}`. Each row is an object keyed by its declared columns. Complete all required pagination or throw. Never silently truncate, manufacture aggregate totals from a sample, or combine nonadditive metrics. Set `metadata.complete:true` only after the full selected report succeeds. Incomplete/truncated results and row-budget overflow are rejected before writing.

For saved-report continuation, a report may additionally declare `fetchChunk(ctx, state)`. The first state is `null`; return `{columns,rows,nextState,metadata}` for one complete provider page. `metadata.complete` must be a boolean and must equal `nextState === null`: unfinished chunks need JSON-serializable cursor state, and the final chunk needs `nextState:null`. Never store credentials, authorization headers or access tokens in that state. Validate resumed state and keep column descriptors identical across chunks. `dmvMergeChunk_` normalizes each page, enforces the aggregate row/size bounds and rejects more than 100 chunks. Retain the complete `fetch(ctx)` interface with `dmvFetchChunks_(ctx, fetchChunk)` so previews still fetch the whole report in one execution. Currently GA4 and GitHub opt in; all other connectors retain their existing single-execution behavior. See [chunk continuation](chunk-continuation.md) for storage, time and recovery limits.

The context supplies validated dates, selected fields/configuration, credentials, the row limit, the absolute `deadline` (a caller such as the chat may pass one so several fetches share it), `checkDeadline()`, `http(request)`, `accessToken()` for declared Google scopes, and `rotateCredentials(patch)` for providers that hand back a replacement secret. The transport enforces exact HTTPS hosts, disables redirects, limits retries and execution time, and keeps credential-bearing errors out of logs. Use `retrySafe:true` only for idempotent read requests. `responseType:'blob'` returns the raw response body (for compressed report downloads) instead of parsed JSON, under the same size guard. A connector's optional `errorMessage(code, body)` may turn any 4xx provider error body into a short actionable message. Do not fetch credentials from a sibling connector.

Providers with their own OAuth refresh flow (LinkedIn, Microsoft) call `dmvOAuthRefreshToken_({label, endpoint, scopes, scopeParameter}, credentials, deadline, ctx.rotateCredentials)`, the same cached exchange the Google OAuth mode uses. When the provider issues a replacement refresh token, `rotateCredentials` updates the in-memory credentials and, for a saved connection whose revision is unchanged, persists the new secret without bumping the revision (so running continuations stay valid). The refresh token is never cached or logged; access tokens are cached per user until shortly before expiry.

Every report is also available to the chat. Declared `fields` with `type` and `role` are the model's schema, so keep labels and roles accurate; `configFields` become the chat's `config` parameters, with their `help` text as the description. Mark metrics that cannot be added across rows with `additive:false` (user counts, reach); rates (`percent`) and names containing ctr, cpc, rate, average and the like are treated as non-additive automatically, and the flag survives normalization, caching and summaries.

The add-on's manifest asks only for spreadsheets, external requests, triggers and the sidebar; it never carries a Google API scope, so `ScriptApp.getOAuthToken()` is never used for a provider. The shared Google authorization fields (`dmvGoogleAuthFields_`) offer `service_account` (the default), `oauth` and `token`; a connector's `googleScopes` are the scopes its own tokens are minted or refreshed with. The **OAuth client credentials** mode (`authMode:'oauth'`) requires `clientId`, `clientSecret` and `refreshToken`; the last two are secret fields and must never appear in summaries, bootstrap data, logs or continuation state. `accessToken()` exchanges the already-authorized refresh token at Google's fixed token endpoint and refreshes access tokens automatically. The refresh token must belong to that client and cover the connector's declared scopes; refresh cannot add a missing grant. A client ID and secret alone do not authorize a source account. See Google's [offline-access contract](https://developers.google.com/identity/protocols/oauth2/web-server#offline).

DataMoov does not host an OAuth callback or issue the initial refresh token. Users configure their own OAuth project's APIs and access approvals, including Google Ads Explorer or higher access for production accounts. Auth fields split in two. Fields flagged `perConnection:true` (account ids such as `customerId`, `propertyId`, `siteUrl`, `adAccountId`, database host and name, chat scope) live on the connection; every other auth field belongs to a **saved credential** the user manages under Settings and picks from a dropdown when connecting. Connectors that share one credential declare `credentialFamily` (the four Google sources use `DMV_GOOGLE_CREDENTIAL`, whose fields come from `dmvGoogleAuthFields_` plus any extra field a connector adds, such as the legacy `developerToken`); otherwise the connector is its own credential type. `dmvReadConnection_` merges the credential's values under the connection's own values before any context is built. `dmvSaveCredential` checks changed Google service-account or OAuth credentials through a token exchange using the family's scopes. It also checks each existing connection using the edited credential when that connector declares a `test` function or Google scopes, with the connector's own connectivity test or token fallback. Older connections may still embed the whole credential; both forms are read the same way. BigQuery's query project and SQL remain report configuration.

When editing the same saved credentials, blank secret fields retain values from that user's saved record; explicit replacements rotate them. Changing OAuth clients requires a matching client secret and refresh token. A credential edit waits until its consuming reports finish refreshing, and any failed available connection check prevents replacing the saved credential. Connector `test` functions must actually reach the provider (Microsoft submits a one-day report request it never downloads), not merely validate configuration. Provider-issued refresh-token rotations for the same OAuth identity are preserved even if a later account check rejects the edit.

New or changed connections use the same declared connectivity test or Google token fallback before persistence. The saved summary carries `verified:true` when a check ran; that flag does not certify every report or account permission. Unused pasted tokens and credentials without an available provider check are saved without a live check. HubSpot and Zendesk currently declare no connection test and require a report preview. BigQuery has no connection-level query configuration, so token verification on save does not prove query-project or dataset access. Label-only edits do not repeat verification. Preserve per-user isolation and never substitute secrets from another connection or return them to the browser.

Reports default to 1,000 rows and cannot exceed 20,000 rows or 80 output columns. The shared `maxBytes` guard rejects a serialized typed matrix longer than 8,000,000 characters. Single-execution fetches must fit their request deadline; continued reports must also fit the private checkpoint limits. Continuation never permits partial output or bypasses final size checks. The writer checks ownership/overlap and submits values, stale-result clearing, and number formats in one Sheets batch. String values are written explicitly as strings, preserving long IDs and preventing formula interpretation. A SHA-256 receipt verifies the previous typed cell values before refresh; manual edits, formulas, shifted/deleted cells, or missing receipts stop replacement. Cells outside the report footprint remain unchanged.

Saved reports are private records of their owner and are never written to the spreadsheet. Keep authentication fields on private credentials or connections, never in report configuration. The report runtime validates the selected connection and query before every execution. See [report storage](report-storage.md).

Continued reports keep fixed resolved dates and report/connection revisions across executions and load credentials anew for each execution. The scheduler uses each user's private reports and schedules; copying or sharing the spreadsheet does not activate a schedule. Hourly refresh also recovers that user's pending continuations, including on-demand reports, and preserves unrelated triggers. Schedules are approximate intervals, not exact-time commitments. Service-account keys and OAuth client credentials with a valid refresh token support unattended refreshes; pasted expiring access tokens require replacement.

Test the real adapter with provider-shaped fixtures for paging, empty results, custom fields, zero/false/null values, row limits, fatal authorization errors, and incomplete data. For chunk-capable reports, also test serialized state round-trips, resumed state validation, stable columns, completion markers and unchanged output before completion. Test shared changes through an arbitrary connector identity. Passing offline tests does not certify live API permissions, billing, Google authorization, or provider-side field availability.

Connectors may declare `connectionKeys` as non-secret `perConnection` field names that identify the source account, database or query context. A connection used by a saved report cannot change those fields; create a new connection instead. This protects SQL sources without requiring an account-discovery UI. Account-discovery selection keys receive the same protection.

Connectors may declare `accountDiscovery: {label, credentialKeys}` and `discoverAccounts(ctx)` to offer **Find accounts**, an optional helper that lists the accounts the entered credentials can reach and fills the selection fields; the fields stay editable and saving never requires a discovered choice. The method returns the complete array of `{id, label, credentials}` choices, where credentials contains only the declared, non-secret selection fields. Follow every page or throw; never return a silently partial list. The generic `dmvDiscoverAccounts` API validates authentication without requiring the selection fields, reuses only the current user's saved secrets, and exposes only the declared selection keys. The UI discards stale asynchronous responses when credentials change. Changing the account behind an existing report requires a new connection. Discovery does not reset or overwrite report output.

Connectors declare a `guide` so the connection form can explain where the credentials come from: `{intro, steps, links: [{label, url}], modes: {authMode: {steps, links}}}`; `dmvGoogleGuide_({apis, access, grant, scope, links})` builds the Google variant with the shared Cloud Console steps. Only `https:` links are rendered. SQL connectors may declare `describeTables(ctx, {search})` returning `{scope, tables: [{name, columns: [{name, type}]}], truncated}` for the chat's `describe_database` tool, reading only the schemas or datasets the user chose on the connection (`chatSchemas` for PostgreSQL, `chatDatasets` for BigQuery). Apply the table-name search inside the query, before any cap, and report `truncated:true` when the cap was hit; both connectors run the listing through their ordinary bounded read-only query path (`dmvTableSearch_` sanitizes the term, `dmvGroupTables_` groups the rows).

Run `npm run check`, `npm test`, and `npm run test:browser` as applicable. Publish only to your recorded development project with `npm run push:dev`.
